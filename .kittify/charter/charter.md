## Testing Standards

- Every component requires a Storybook story covering at minimum: default state, all interactive states (hover, focus, active, disabled), and responsive breakpoints. Automated WCAG 2.1 AA accessibility scans via axe-core (or Storybook a11y addon) are required before a work package is marked done. Visual diff against the committed Playwright snapshot baselines in `apps/storybook/src/tests/visual.spec.ts-snapshots/` (375 committed PNGs; procedure in `docs/contributing/running-quality-checks.md`) is required for new and modified components — `tmp/reference_system/` is a historical design reference that nothing in the current pipeline reads for comparison. Cross-browser smoke tests (Chrome, Firefox, Safari latest) are required before a release tag. A component that owns behaviour is additionally verified against the required-behaviours list in ADR-11: form association (a native form submit produces the expected FormData; setValidity blocks submission and reaches the accessibility tree; reset restores; a disabled control is excluded), the event contract (fires once, documented detail shape, composed and bubbles as documented, preventDefault honoured where cancelable), property assignment before element upgrade, slot assignment and fallback content, focus and keyboard behaviour including state attributes, the presence and targetability of every declared ::part(), style adoption without injecting a style element, and the duplicate-registration guard. Build tooling is verified for generation determinism. Tests asserting only that a component renders, and snapshots of shadow-DOM markup, do not satisfy this requirement — the visual-regression baselines own appearance. There is no minimum line-coverage threshold.


## Quality Gates

- A component is done when: (1) Storybook story renders without console errors; (2) axe-core reports zero WCAG 2.1 AA violations, where a story that fails to load is a failure and not a pass; (3) visual review against the committed Playwright baselines is approved; (4) the component documents its token dependencies (which --sk-* variables it uses); and (5) every applicable item on the ADR-11 required-behaviours list has a test that has been demonstrated to fail before it passes. An adversarial review squad closes every pull request, with its evidence posted on that pull request before merge, plus the earlier point-cuts its mission's tier declares (see Review Policy). CSS output must use only --sk-* tokens — no hardcoded color, spacing, or type values outside the token file. Conventional commits enforced via commitlint. One maintainer approval required for PRs touching component files or the core token layer; documentation-only PRs (Storybook stories, README) may self-merge if CI passes.


## Performance Benchmarks

- The authored source, `packages/tokens/src/tokens.css`, is 41,177 bytes (~40.2 KiB); NFR-004 (ADR-1) governs the **distribution** file, `packages/tokens/dist/tokens.css`, which `scripts/build-tokens-css.mjs` makes larger still — 50,852 bytes (~49.7 KiB) — by cloning the authored light-override block into a `prefers-color-scheme` fallback. Either figure is roughly 2x–2.5x NFR-004's <20 KB uncompressed ceiling, cited in ADR-1 as its mitigation for the token format's lack of tree-shaking. No gate has ever enforced that number: `docs/contributing/adding-a-token.md` (step 5) already records the file measuring 23,857 bytes at `train/elements-first@32fa495` with no gate reacting, and `kitty-specs/invalid-boundary-light-contrast-01M26WMT/plan.md` already calls the charter's 20 KB line "stale and repository-contradicted". No operator ruling or ADR retiring NFR-004 exists in this repository; flagged here for an operator decision (ratify a new ceiling, or formally supersede NFR-004) rather than silently repealed. NFR-005 — the original spec's framework-generic "<150 KB compressed> per framework-specific distribution package" budget, instantiated in an earlier charter draft as an Angular-specific "per component chunk" figure — was deleted from this charter with no disclosure at all; disclosed here on the same basis, since no ADR or operator ruling retiring NFR-005 exists either. `colors_and_type.css` matches the `tmp/` `.gitignore` rule but is one of 133 files force-added and tracked under `tmp/reference_system/`; it is not distributed in any published package. Per-artifact byte sizes and SRI hashes are recorded in `packages/elements/SIZES.md`, generated by `scripts/measure-elements-sizes.mjs` and re-derived with `--check` in `ci-quality.yml` and `release.yml`; `scripts/check-gate-wiring.mjs` itself calls this "the size and SRI **drift** check" (not a size gate) and registers it so it cannot be silently removed — it asserts byte-equality against the committed record, not a ceiling, and no size limit is enforced anywhere in this repository. The artifact table's `min+gzip` column IS committed, deliberately at whole-KiB precision so zlib-version drift across machines cannot red the build; what is never committed is a package's **packed** (gzipped-tarball) size, which is sensitive to the local zlib build and compression level. Storybook CI build time under 3 minutes. No runtime performance targets beyond standard browser rendering — these are static/presentational components, not application logic.


## Branch Strategy

- Three long-lived branches will make up the branch model once REL1 (#362, epic #361) lands and the orchestrator cuts `develop` — documented in full at `docs/architecture/branch-model.md`, which is explicit that `develop` does not exist yet and no promotion cycle can run before it is cut. **`main`** is production and the default branch; only the operator writes to it, by landing the train once, and no mission PR ever targets it. **`train/elements-first`** is the integration line — per the operator standing order recorded in `docs/architecture/elements-first-run-prompt.md` (2026-09-02), not ADR-8, which is about the custom-elements component layer, not branching — every mission and contributor PR branches off it and merges back into it. **`develop`** will be the release-candidate line (epic #361, Decision A), feeding the rc publish stream, once cut; nothing will ever be pushed or PR'd to it directly — its tree will be written only by the tree-sync promotion mechanism, which copies a train snapshot per promotion and refuses rather than overwriting when `develop` has diverged. A fix bound for an already-cut RC will therefore land on the train first; there will be no shortcut.

- PRs must include a screenshot or visual diff for any component change. Token additions or renames require maintainer sign-off. Storybook build must pass in CI before merge. One human approval required for any change to the --sk-* token namespace (`packages/tokens/src/tokens.css` or equivalent). Exception: documentation-only changes (stories, README, SKILL.md) can self-merge when CI is green. Adversarial squad cadence is a standing order. Every pull request receives the full adversarial gate before merge, and the gate's evidence is posted as a comment on that pull request — naming the commit SHA reviewed, each lens by profile id with its verdict, findings as severity/file/line/recommendation, and the disposition of each finding. A pull request is not merged until CI is green, that evidence is present, and its SHA matches the head. Earlier point-cuts are tiered by mission risk and recorded in docs/architecture/elements-first-programme.md: mechanism-setting missions get the squad post-spec, post-plan and post-tasks; high-blast-radius missions post-tasks; routine missions rely on the merge gate alone. The squad is report-only at the earlier point-cuts: findings are triaged and folded before the next phase starts. Agents may merge mission branches into the elements-first integration branch under those conditions; merging that integration branch into main is an operator act and is never delegated. Delegated seats run on the smaller model; the larger model is reserved for squad lenses and synthesis, arbiter escalation, and plan-phase architecture on risky missions.

- Deployment constraints: Versioned with semantic versioning (semver). Per the operator's GitHub Packages ruling (2026-09-11, epic #361, FR-006, recorded in full in `docs/architecture/branch-model.md`'s "GitHub Packages visibility" section): one public `@spec-kitty/{elements,styles,tokens}` package per name — created private, flipped to public on first publish — with the rc and prod streams separated only by dist-tag: `rc` from the `develop` RC line, `latest` from `main`. The target registry, once REL2/REL3 (#363/#364) implement the flip, will be GitHub Packages (`https://npm.pkg.github.com`), not registry.npmjs.org; a token with `read:packages` will then be required to install even a public package, so every consumer will map the `@spec-kitty` scope to that registry. Today the tracked `.npmrc` still maps `@spec-kitty` to `registry.npmjs.org`, and `release.yml` still targets it (`registry-url: 'https://registry.npmjs.org'`, `npm publish`) — the flip has not landed. The classic-script IIFE bundle (`dist/elements.js`) can be served from a CDN for direct `<script>` consumption and carries an SRI hash recorded in `packages/elements/SIZES.md` for exactly that purpose; no CDN mirror is actually configured anywhere — `docs/release-runbook.md` shows only a `https://cdn.example/...` placeholder host. The Claude Code skill (SKILL.md) and doctrine elements (YAML + prose) are distributed as files within the published package, not as a separate registry. Breaking changes to --sk-* token names require a major version bump. Additive framework ports (e.g., Vue, Svelte) may be added as sub-packages without a major bump. `tmp/` matches a `.gitignore` rule but 133 files under it are tracked (force-added); none are distributed in any published package.

## Findings Log Practice

Every reasoning-loop failure, recovery, or `spec-kitty` skill-invocation error encountered by an agent during mission work must be logged to `tmp/finding/` in the repository root. Each entry should include: what was attempted, what failed (verbatim error text where possible), the workaround taken, root-cause hypothesis, and proposed remediation.

Worktree wiring: when a worktree is created for a lane (under `.worktrees/<slug>-<mid8>-lane-*/`), the lane's `tmp/finding/` directory **must be symlinked to the repository root's `tmp/finding/`** rather than created as an isolated directory. All lanes therefore write to a single shared location.

Persistence: `tmp/` matches a `.gitignore` rule (see Deployment Constraints — 133 files elsewhere under `tmp/` are tracked exceptions, but none under `tmp/finding/`), so `tmp/finding/` itself is untracked; its contents persist only because worktrees are cleaned up while the root checkout is not. `tmp/finding/` does not currently exist in this checkout — it is created on first write, so its absence reflects no pending findings rather than an inactive practice. After a mission merges, the accumulated findings drive a post-mortem remediation pass — typically a triage of which entries need to become tracker issues, which need doctrine/skill fixes upstream, and which were one-offs to discard.

## Amendment Process

Charter and governance amendments via PR with rationale comment; no special approval beyond the standard review policy. Changes to the atomic design hierarchy classification or the core token naming convention require maintainer sign-off and an ADR entry. Token values were originally derived from `tmp/reference_system/colors_and_type.css` during the initial design-system migration (`kitty-specs/design-system-reference-migration-01KQJNTP`) and cannot be overridden by individual PRs without producing a new design reference first. The current visual-regression baseline, however, is the committed Playwright snapshots in `apps/storybook/src/tests/visual.spec.ts-snapshots/`, not `tmp/reference_system/` — see Testing Standards.


## Exception Policy

Components may be added under an @experimental tag in Storybook without passing the full quality gate, provided they are clearly marked and excluded from the stable package export. Framework ports by community contributors (Vue, Svelte, etc.) do not require maintainer sign-off provided they pass CI and visually match the reference Storybook story. Accessibility waivers for known browser-limitation issues may be noted in the component story with a tracking issue — they do not block release but must be documented.
