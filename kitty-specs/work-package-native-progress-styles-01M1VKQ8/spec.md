# Mission Specification: work package native progress styles

**Mission Branch**: `mission/work-package-native-progress-styles`
**Created**: 2026-09-06
**Status**: Draft
**Issue**: [#210](https://github.com/spec-kitty/spec-kitty-design/issues/210) `[TKW2] native progress styles — accessible completion over real <progress>` · child of [#208](https://github.com/spec-kitty/spec-kitty-design/issues/208) · tracks #125
**Base**: `train/elements-first@32fa495`
**Input**: GitHub issue #210, squad tier C (pre-merge only)

## Context

The Factory Dashboard hand-rolls its own completion indicator today —
`apps/demo/dashboard-demo.html`'s `.dash-progress-group` / `.dash-progress-bar` /
`.dash-progress-fill` / `.dash-progress-label` — as three plain `div`s and a `span`, with the
fraction expressed only as an inline `style="width: 67%"` and a `title` attribute. A `title` is not
an accessible name and is not reliably exposed to assistive technology; there is no `role`,
no exposed value, and no label association of any kind. `grep` against `tokens.css` finds zero
`progress`-prefixed tokens and no issue numbered 66 or later already owns this gap.

The platform already solves this: `<progress>` is a native, form-adjacent element with an implicit
`progressbar` role and `aria-valuenow`/`aria-valuemin`/`aria-valuemax` computed by the browser from
its own `value`/`max` attributes (min is implicitly `0`). This mission adds a **styles-only**
`.sk-progress` family — CSS plus authored static markup — that presents that native element with the
library's visual language, exactly as `research.md` (already authored for this mission) determined.
No custom element ships. This document does not re-derive that architecture call; it specifies the
observable behaviour the styles-only family must have, so the decision already made in research and
in ADR-10's styles-only class ruling can be planned and implemented against.

Representative structure, verbatim from #210:

```html
<div class="sk-progress">
  <label class="sk-progress__label" for="mission-progress">5 of 8 Work Packages done</label>
  <progress class="sk-progress__bar" id="mission-progress" value="5" max="8">63%</progress>
  <span class="sk-progress__meta">63%</span>
</div>
```

## User Scenarios & Testing *(mandatory)*

### User Story 1 — a consumer composes one accessible progress indicator from plain markup (Priority: P1)

A page author building a mission-completion widget writes the three-part markup above by hand,
substituting their own `id`, `value`, `max`, label text and visible metadata text. They apply no
JavaScript and perform no arithmetic in the markup itself — the numerator, denominator, label copy
and displayed percentage are all values the author already has.

**Why this priority**: this is the mission's entire outcome. Every other story is a property this
same markup must keep under a different condition.

**Independent Test**: render each required determinate-state fixture (zero, the T10 5-of-8 worked
example, complete, a large total, a long label) from the generated styles-only barrel, and confirm
each is exactly the three-part structure — `label[for]` + `progress[id][value][max]` + `span` — with
no element added, removed, or reordered between fixtures.

**Acceptance Scenarios**:

1. **Given** a fixture with `value="5" max="8"`, **When** it renders, **Then** the `<progress>`
   element's own `value` and `max` attributes read `5` and `8`, and no CSS rule or generated content
   sets or overrides either.
2. **Given** any determinate-state fixture, **When** its markup is inspected, **Then** the visible
   `sk-progress__meta` text and the fallback text between the `<progress>` tags are both present as
   separate, independently authored strings — neither is generated by the stylesheet.
3. **Given** the zero-value fixture (`value="0"`), **When** it renders, **Then** the track is visible
   and the fill occupies no visible width.
4. **Given** the complete fixture (`value` equal to `max`), **When** it renders, **Then** the fill
   visually reaches the full width of the track.

### User Story 2 — a screen-reader user perceives role, name, and value from native semantics alone (Priority: P1)

A screen-reader user tabs to or reads past the progress indicator. They hear its role
("progress indicator" or equivalent, per the user agent), its accessible name (the associated label
text), and its current value expressed against its minimum and maximum — all without the page author
having written a single ARIA attribute.

**Why this priority**: this is #210's explicit accessibility-tree requirement and the reason a native
`<progress>` was chosen over a hand-rolled `div` in the first place — the dashboard's existing
`.dash-progress-bar` gives a sighted user a bar and a screen-reader user nothing.

**Independent Test**: query the accessibility tree of the T10 worked-example fixture and assert its
role, accessible name, and numeric value/min/max match the `label` text and the `progress` element's
own attributes, with no `aria-*` attribute present anywhere in the fixture.

**Acceptance Scenarios**:

1. **Given** the T10 fixture (`label` text "5 of 8 Work Packages done", `progress value="5" max="8"`),
   **When** the accessibility tree is queried, **Then** the control's role is the platform's native
   progress-indicator role, its accessible name is "5 of 8 Work Packages done", and its exposed
   value/min/max correspond to `5`/`0`/`8`.
2. **Given** any fixture in this mission, **When** its markup is inspected, **Then** it contains no
   `aria-label`, `aria-labelledby`, or `role` attribute — the `label`/`progress` `for`/`id` pair is
   the sole association mechanism.
3. **Given** axe-core is run against every story this mission adds, **Then** it reports zero WCAG
   2.1 AA violations, in both the default (dark) and `LightMode` presentations.

---

### User Story 3 — a consumer picks a layout arrangement without changing markup shape (Priority: P2)

A consumer placing the indicator inline beside other compact metadata applies a
`sk-progress--compact` modifier class; a consumer stacking it in a narrow column applies
`sk-progress--narrow`. In both cases they keep authoring the same three children in the same order —
only the CSS layout changes.

**Why this priority**: #210 requires both arrangements to "preserve the same native element and
label" — a consumer must never have to choose between the accessible markup and the layout they need.

**Independent Test**: apply each modifier class to the same underlying markup and confirm the
`label`/`progress`/`span` triad, their attributes, and their document order are unchanged from the
unmodified fixture — only computed layout (flex direction, stacking) differs.

**Acceptance Scenarios**:

1. **Given** the base three-part markup, **When** `sk-progress--compact` is applied, **Then** the
   same three children in the same order render in an inline/flex-row arrangement.
2. **Given** the base three-part markup, **When** `sk-progress--narrow` is applied, **Then** the same
   three children in the same order render stacked, and no child is dropped, duplicated, or moved to
   a different parent.
3. **Given** either modifier, **When** the accessibility tree is queried, **Then** the role,
   accessible name, and value/min/max are identical to the unmodified fixture's.

---

### User Story 4 — completion stays legible at zoom, under forced colors, and without relying on hue (Priority: P2)

A low-vision user browsing at high zoom, and a Windows High Contrast (forced-colors) user, must both
be able to tell the track from the fill and read the label and metadata text — and a user who cannot
distinguish hue must not be relying on color alone to tell "some progress" from "no progress" or
"complete."

**Why this priority**: #210 states this as a binding constraint ("legible at zoom and in forced
colors; completion is not conveyed only by hue") and it is the class of defect that a color-only
treatment produces silently, with no lint rule to catch it.

**Independent Test**: render the long-label and large-total fixtures at a zoomed/narrow viewport and
assert the page does not scroll horizontally; emulate `forced-colors: active` over a determinate
fixture and assert the track's boundary and the fill are each still distinguishable from the page
background and from each other.

**Acceptance Scenarios**:

1. **Given** the long-label fixture, **When** the viewport is narrowed or zoomed, **Then** the page's
   horizontal scroll width equals its viewport width — the label wraps or truncates rather than
   forcing overflow.
2. **Given** the large-total fixture (large `value`/`max` numerals in the label and meta text),
   **When** it renders at the same conditions, **Then** the same no-horizontal-overflow property
   holds.
3. **Given** a determinate fixture, **When** `forced-colors: active` is emulated, **Then** the
   track's outer boundary remains visible (a bordered edge, which a plain `border` already receives
   from the browser's automatic system-color remapping) and the fill remains visible against the
   track (an explicit system-color override, since a `background`-drawn fill does not survive forced
   colors unaided).
4. **Given** the same forced-colors condition, **When** compared against the normal rendering,
   **Then** no information is lost that hue alone was carrying — track and fill remain distinguishable
   by their boundary/fill treatment, not by color alone in either mode.

---

### User Story 5 — a motion-sensitive consumer sees no animated fill change (Priority: P3)

A consumer who later mutates an existing fixture's `value` attribute from their own script (a
usage this mission's static fixtures do not themselves exercise, but that the shipped CSS must
still handle correctly) does so for a user who has requested reduced motion. That user sees the fill
update instantly, with no transition.

**Why this priority**: #210 states "any transition is disabled under reduced motion" as a binding
constraint. It is lower priority than the stories above only because none of this mission's own
static fixtures trigger a transition — the requirement governs the shipped CSS's correctness, not an
interaction this mission's own test fixtures perform.

**Independent Test**: inspect the authored CSS (if a fill transition is authored at all) for a
`@media (prefers-reduced-motion: reduce)` block that disables exactly that transitioning declaration
on exactly the selector that owns it.

**Acceptance Scenarios**:

1. **Given** the authored `sk-progress.css` declares a transition on the fill, **When** the
   stylesheet is inspected under `prefers-reduced-motion: reduce`, **Then** that specific transition
   is disabled and no other, unrelated selector's transition is affected.
2. **Given** no transition is authored on the fill at all, **When** the stylesheet is inspected,
   **Then** this story is satisfied vacuously and no reduced-motion block is required for a property
   that does not exist — consistent with `adding-a-component.md`'s warning against a guard that
   disables nothing.

### Edge Cases

- **Invalid consumer data (negative value, value exceeding max).** Explicitly out of scope for this
  component to prevent or correct — #210 states this is consumer validation. No fixture in this
  mission demonstrates an invalid value, and no CSS or markup mechanism enforces domain validity.
- **Fallback content vs. visible metadata are two different texts.** The text between
  `<progress>...</progress>` tags is fallback content for a non-rendering user agent, not part of the
  accessible name or the sighted-visible metadata; `sk-progress__meta` is the sighted, styled
  duplicate. Both are authored per fixture; neither is derived from the other.
- **A fixture's visible metadata must not silently drift from its own `value`/`max`.** Every
  maintained fixture's `sk-progress__meta` text expresses the same raw numerator/denominator or
  percentage as its own `progress` element's `value`/`max` pair. This is a property of the maintained
  fixture set, verified by a test reading both texts — it is not a runtime guarantee the component
  can enforce, since there is no code path a consumer's own markup passes through.
- **Large numerals in a compact or narrow arrangement.** The large-total fixture must not visually
  break either layout modifier — checked by combining the large-total state with each modifier where
  practical, or by confirming the modifiers' CSS rules do not assume a numeral width.
- **A component that owns no state has no "changing" `value` to test live.** Every fixture is a
  static snapshot. Nothing in this mission asserts behaviour over time; NFR/AC language about
  transitions concerns the CSS as authored, not an animation this mission's own stories perform.

### Key Entities

This mission introduces no domain entity, no reactive property, no event, and no application state —
see `data-model.md` (already authored for this mission) for the full reasoning. The closest analogue
to a data model is the fixed markup and attribute contract every fixture instantiates:

| Part | Element | Consumer-supplied | Notes |
|---|---|---|---|
| Root | `div.sk-progress[ sk-progress--<modifier>]` | none | Carries layout modifiers only; no ARIA role |
| Label | `label.sk-progress__label` | `for="<id>"`, text content | Native `for`/`id` association; copy is entirely consumer-owned |
| Control | `progress.sk-progress__bar` | `id="<id>"`, `value`, `max`, fallback text | Native `<progress>`; role and `aria-valuenow`/`valuemin`/`valuemax` derive from the element's own attributes |
| Meta | `span.sk-progress__meta` | text content | Visible, styled duplicate of the same numerator/denominator for sighted users |

No modifier changes which children exist, their order, or their attributes — only CSS layout.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `packages/styles/src/progress/sk-progress.css` exists with a **generated** `index.ts`
  barrel, and `packages/elements/src/progress/` does not exist. Verified by
  `node scripts/build-styles-only-markup.mjs --check` passing on a clean tree and
  `git ls-files packages/elements/src` showing no `progress` directory.
- **SC-002**: The generated barrel exports one HTML constant per authored fixture, covering at least
  every state FR-006 and FR-007 name: zero, T10 5-of-8, complete, large total, long label, compact,
  narrow — with default (dark) and `LightMode` presented as story-level treatments of the same
  fixtures, and forced-colors legibility demonstrated over a determinate fixture, matching this
  repository's own convention for how existing styles-only components (`facts`, `disclosure`,
  `data-table`) present dark/LightMode/forced-colors without a bespoke fixture file for each.
- **SC-003**: Every fixture's accessible name, role, and value/min/max are asserted against its own
  `label` text and `progress` attributes, with zero `aria-*` attributes present in any fixture's
  markup.
- **SC-004**: axe-core reports zero WCAG 2.1 AA violations on every story this mission adds, in both
  default and `LightMode`.
- **SC-005**: The long-label and large-total fixtures produce no horizontal page overflow
  (`document.documentElement.scrollWidth` equal to viewport width) at a narrow viewport and under
  emulated high zoom.
- **SC-006**: Under `forced-colors: active` emulation, a determinate fixture's track boundary and
  fill are each still distinguishable from the page background and from each other.
- **SC-007**: For every maintained fixture, the `sk-progress__meta` text and the `progress[value]`/
  `progress[max]` pair express the same raw numerator/denominator or percentage — asserted by a
  test, not merely eyeballed.
- **SC-008**: `packages/styles/src/index.ts` exports the new component, and
  `packages/styles/package.json` carries a `./progress/*` subpath export — verified by
  `scripts/check-release-graph.mjs`'s subpath-coverage check, which refuses any component directory
  lacking one.
- **SC-009**: `stylelint`, `htmlhint`, and the generated-artifact `--check` scripts all pass with no
  new exception beyond the repository's already-recorded forced-colors system-color keywords used on
  longhand `-color` properties.
- **SC-010**: No entry is added to `expected-parts.json`, `expected-docs.json`, `behaviours.json`, or
  `mutations.json` for this component — those ratchets govern the element layer, which this component
  does not have.
- **SC-011**: No `--sk-*` token is introduced unless implementation records a demonstrated gap and
  the accompanying maintainer sign-off; verified by `git diff` against `packages/tokens/src/tokens.css`
  showing no new declaration, absent such a recorded exception.
- **SC-012**: `apps/demo/dashboard-demo.html` has no diff from this mission.

## Out of scope

A custom `sk-progress` element or any `packages/elements/src/progress/` source. Progress
calculation, percentage derivation, or any arithmetic performed by CSS or markup. Timers, polling, or
any JavaScript. Indeterminate/loading state, a stepper component, task data, completion animation, or
status-tone colour coding. A new `--sk-*` token category absent a demonstrated gap. Migrating
`apps/demo/dashboard-demo.html` to consume `sk-progress` (reserved for #214/TKW6). Any composition
with other `#208` children — this mission's markup and CSS are self-contained.

## Open questions

None block this specification. Two items are recorded as execution risk rather than unresolved
product decisions, both already flagged in `research.md`: the forced-colors fill override is
pattern-following from two prior components but not yet measured against a real `<progress>`
element's vendor-prefixed pseudo-elements specifically, and cross-browser coverage of
`::-webkit-progress-bar`/`::-webkit-progress-value`/`::-moz-progress-bar` has no single standard
equivalent and needs both authored. Both are implementation/verification concerns for the plan and
tasks phases, not forks this specification needs to resolve.
