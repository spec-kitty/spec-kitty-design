## Summary

Add a **styles-only** CSS class family, `sk-segmented-choice`, to `@spec-kitty/styles`, so a Team Kitty
consumer can wrap a row of their own `<button type="button" aria-pressed="…">` elements and have them
render as one visually coherent, accessibly distinct segmented control — with zero JavaScript, zero ARIA,
and zero application state owned by the library (FR-001/FR-002, "Application ownership" section). The
technical approach is the same generation pipeline already proven by `sk-form-select`, `sk-disclosure`,
`sk-data-table`, `sk-skip-link`, and `sk-facts`: an authored `.css` file plus hand-authored `.html`
exemplars in `packages/styles/src/segmented-choice/`, a barrel (`index.ts`) generated by
`node scripts/build-styles-only-markup.mjs`, and a Storybook stories file consuming that barrel's exports.
No `packages/elements/src/segmented-choice/` directory, no Lit class, no manifest entry, no `::part()`,
no generated React/Vue wrapper output (C-001, C-002, FR-010). One Work Package, one PR, targeting
`train/elements-first` (C-007).

### IC-01 — CSS authoring, tokens-only, base + interaction states

- **Purpose**: Author `sk-segmented-choice.css`: `.sk-segmented-choice` (group container, flex-wrap
  layout, no assumption of item count — FR requires 2/3/5-item correctness), `.sk-segmented-choice__item`
  (per-button styling reading `[aria-pressed="true"]` and `:disabled` as pure selectors — FR-001/FR-002),
  pressed/hover/active/focus-visible/disabled states each distinguished by more than colour (FR-003).
- **Relevant requirements**: FR-001, FR-002, FR-003, FR-004, FR-005, FR-015, NFR-002, NFR-003, C-003, C-004.
- **Affected surfaces**: `packages/styles/src/segmented-choice/sk-segmented-choice.css`.
- **Sequencing/depends-on**: none — this is the first concern, but its red-first tests (IC-04's Playwright
  live-block selected/hover/active/focus assertions, written against the *planned* selector contract
  before the CSS ships the distinguishing declarations) must exist and fail before this CSS lands the fix,
  per DIRECTIVE_041. In practice, the real order (see IC-04's Sequencing/depends-on for the full
  static-Storybook rationale): author the `.html` exemplars (IC-02), a minimal/undifferentiated first CSS
  pass (this IC), and a first-pass Storybook stories file (IC-05, story ids may still be adjusted)
  together, run `npx nx run storybook:storybook:build` so the story ids IC-04's live block opens via
  `page.goto` actually exist, THEN write and run the Playwright spec's live-block selected/hover/active/
  focus/disabled assertions (IC-04) — including the pressed-item computed-style-delta assertion for FR-003
  (border/font-weight/shape against an unpressed sibling, not colour alone) — against that
  minimal/undifferentiated pass and watch them fail (no visible cue delta), THEN add the distinguishing CSS
  declarations (border/weight/shape per FR-003) until the same assertions pass. Token choice: pressed fill
  is `var(--sk-bg-pill)` (matching
  `.sk-nav-pill__item--active { background: var(--sk-bg-pill); }` in `sk-nav-pill.css`), plus existing
  border/focus token families (`--sk-border-*`, `--sk-border-focus`) — no new component-named token, no
  `--sk-surface-pill` (FR-015/C-004).
- **Risks**: Base-state token reuse only — `sk-nav-pill.css`/`sk-form-select.css` carry no `forced-colors`
  block, so C-004 explicitly does not treat them as forced-colors precedent (that's IC-03's job). Getting
  the 44px narrow-viewport minimum (NFR-002) without inflating default density (User Story 2, Acceptance
  Scenario 3) needs a viewport-scoped size rule, not a permanent enlargement — verified live by IC-04's
  Playwright measurement at exactly 1024px, not assumed from the CSS source.

### IC-03 — Forced-colors CSS

- **Purpose**: Add the `@media (forced-colors: active)` block to `sk-segmented-choice.css`, using the
  LONGHAND `-color` technique (never `border`/`outline` shorthand) for the selected-state indicator, the
  focus-visible indicator, AND the disabled-state indicator — User Story 4 Acceptance Scenario 4 is
  binding and names all three ("the selected, disabled and focus-visible states each remain
  distinguishable"), not just the two NFR-004's own narrower text enumerates — with system-color keywords
  (`Highlight`, `HighlightText`, `ButtonText`, `CanvasText`, `GrayText`, etc. as measured-appropriate) —
  following `sk-skip-link.css`'s `outline-color: Highlight;` and `sk-data-table.css`'s
  `border-left-color: Canvas/CanvasText/Highlight` pattern for the selected/focus-visible cues, and
  `sk-context-nav.css`'s existing `GrayText` longhand `-color` technique (research.md Q4/EV-032) as the
  precedent for the disabled-state cue.
- **Relevant requirements**: NFR-004, C-010, FR-006 story 11 (forced colors), User Story 4 Acceptance
  Scenario 4.
- **Affected surfaces**: `packages/styles/src/segmented-choice/sk-segmented-choice.css` (forced-colors
  block only), `stylelint.config.mjs` (`ignoreValues` — add only the specific system-color keywords used,
  if not already present; `Canvas`/`CanvasText`/`Highlight`/`HighlightText`/`ButtonText`/`LinkText`/
  `GrayText` are already listed, so this is likely a no-op addition, confirmed at implement time by
  diffing the keywords actually used against that array), and `npx nx run tokens:catalogue` re-run ONLY if
  `stylelint.config.mjs` changes (it does not gate on the token catalogue, but re-running costs nothing and
  keeps the catalogue-dependent stylelint run consistent per CLAUDE.md §4's note).
- **Sequencing/depends-on**: IC-01 (needs the base selected/focus-visible selectors to exist first — the
  forced-colors block overrides them, it does not invent new selectors) and, for the live-block assertions
  below, also IC-05 plus a Storybook rebuild — the forced-colors story id must exist in the built,
  STATIC Storybook before Playwright's `page.goto` can open it (see IC-04's Sequencing/depends-on for the
  full rationale). Red-first, in order: once IC-01 (minimal CSS) + IC-02 (exemplars/barrel) + a first-pass
  IC-05 + `storybook:storybook:build` have landed, write `sk-notice-forced-colors.spec.ts`-pattern
  assertions in IC-04 against the IC-01-only CSS (no forced-colors block yet) and confirm they fail — the
  selected/focus/disabled cues collapse to indistinguishable under `forced-colors: active` emulation

- **Risks**: A background-painted cue frozen with `forced-color-adjust: none` would be the exact trap
  `docs/contributing/adding-a-component.md`'s forced-colors section and NFR-004 name — this plan commits to
  border/outline-drawn cues only, no `forced-color-adjust: none` anywhere in this component's CSS.
