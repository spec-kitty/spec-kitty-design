## Summary

Add one styles-only `sk-checkbox-choice-group` class family to `@spec-kitty/styles`. Author one
token-only CSS source and native HTML exemplars; generate the component barrel with the existing
styles-only generator; document and demonstrate the family in Storybook; and add Playwright,
axe, accessibility-tree, containment, forced-colors, zoom, and visual-regression evidence. No
custom element or JavaScript is added. The complete change is one cohesive Work Package and one PR
to `train/elements-first`.

## Engineering Alignment

- The native form tree is the architecture: fieldset -> legend plus choices wrapper -> labels ->
  checkbox inputs and visible text. No shadow boundary or ARIA replacement is introduced.
- Browser state is authoritative. Styling reads `:checked`, `:disabled`, `:hover`, `:active`, and
  `:focus-visible`; it does not write or synchronize state.
- The public BEM vocabulary is intentionally small and domain-neutral:
  `.sk-checkbox-choice-group`, `__legend`, `__options`, `__choice`, `__control`, `__label`, and
  `__metadata`.
- K3 lane names/counts are fixture content only. The component accepts no data and exports no lane
  vocabulary.
- Existing disclosure and button/action surfaces are composed in the K3 story; their CSS and
  behavior are neither copied nor extended.
- The plan adds no token unless implementation proves that every current semantic token is
  unsuitable. The expected path is reuse only.

## Public Contract

The maintained markup uses this shape:

```html
<fieldset class="sk-checkbox-choice-group">
  <legend class="sk-checkbox-choice-group__legend">...</legend>
  <div class="sk-checkbox-choice-group__options">
    <label class="sk-checkbox-choice-group__choice">
      <input class="sk-checkbox-choice-group__control" type="checkbox" name="..." value="...">
      <span class="sk-checkbox-choice-group__label">...</span>
      <span class="sk-checkbox-choice-group__metadata">...</span>
    </label>
  </div>
</fieldset>
```

`__metadata` is optional. Consumers may omit it, author text other than a count, check or disable any
input, and choose names/values/order. Consumers must author the group legend and visible labels.
The class family does not require a particular option count.

## Implementation Concern Map

### IC-01 - Native markup and styles-only distribution

- **Purpose**: Author the five reusable semantic exemplars, generate their barrel, add the package
  subpath/root exports, and positively assert absence from every element/wrapper surface.
- **Requirements**: FR-001, FR-002, FR-003, FR-010; C-001, C-005, C-007.
- **Affected surfaces**: `packages/styles/src/checkbox-choice-group/**`, styles package exports,
  existing package exports. The styles-only generator itself is expected to remain unchanged.
- **Sequencing**: Start with a source-contract test that fails because the directory/public export
  does not exist; author exemplars; run the generator; make the same test green.
- **Risk**: Hand-editing generated `index.ts` or adding an element by habit. The generator check and
  explicit absence assertions fail both errors.

### IC-02 - Token-driven layout and state presentation

- **Purpose**: Implement the seven-selector BEM family using intrinsic grid collapse, local text
  wrapping, native checkbox visibility, and non-color-only checked/hover/active/focus/disabled cues.
- **Requirements**: FR-004, FR-007, FR-008; NFR-001, NFR-004, NFR-005, NFR-006; C-006, C-008.
- **Affected surface**: `sk-checkbox-choice-group.css` only.
- **Sequencing**: Author browser assertions against a deliberately minimal structural pass, observe
  the missing state/containment claims red, then add the state declarations until green.
- **Risk**: `appearance: none`, hidden inputs, or pseudo-checkboxes would violate the contract even
  if screenshots look right. Source/DOM tests explicitly reject those techniques.

### IC-03 - Storybook composition and immutable examples

- **Purpose**: Expose the 12 story ids from generated exemplars, including the K3 composition with
  existing disclosure and button/action surfaces.
- **Requirements**: FR-009, FR-016; C-002, C-003, C-004.
- **Affected surfaces**: component story file and `expected-stories.json`.
- **Sequencing**: Generate the exemplar barrel first; build Storybook and reconcile actual ids;
  then add browser/visual assertions.
- **Risk**: Story-only JavaScript that simulates filtering or reset would smuggle application
  behavior into the library. Story interaction is limited to focusing or exercising native form
  behavior inside tests.

### IC-04 - Browser, accessibility, and containment proof

- **Purpose**: Verify semantic roles/names/order; Space and label activation; submission/reset;
  disabled exclusion; checked-state preservation; state style deltas; axe; accessibility tree;
  narrow/long/200% containment; forced colors; and focus clipping.
- **Requirements**: FR-005, FR-006, FR-011, FR-012, FR-013; NFR-002 through NFR-006.
- **Affected surfaces**: new Playwright spec and zoom evidence record.
- **Sequencing**: Source-contract tests first, live tests after the first Storybook build, final
  accessibility and manual zoom evidence after final CSS.
- **Risk**: CSS zoom is not equivalent to browser zoom. Use the repository's established real
  browser-zoom evidence method and record viewport/zoom, scroll metrics, reviewed SHA, screenshot
  hashes, and focus result.

### IC-05 - Visual regression and visual inspection

- **Purpose**: Add final-state visual cases for dark, light, narrow, long, disabled, focus,
  forced-colors, 200%-zoom evidence, and K3 composition; compare against the approved K3 evidence.
- **Requirements**: FR-014; NFR-006; C-010.
- **Affected surfaces**: `visual.spec.ts`, generated snapshot files, validation evidence.
- **Sequencing**: Author visual tests only after functional CSS is stable; obtain CI-authoritative
  baselines/diffs; inspect every required story at the final head.
- **Risk**: The UX mockup contains raw values and weaker semantics. Match hierarchy/rhythm/state
  separation while using current tokens and the issue's stronger native structure.

### IC-06 - Documentation, gates, and clean-tree closeout

- **Purpose**: Document markup/token/application-ownership rules; run all affected and repository
  gates; verify generated no-op surfaces and a clean tree.
- **Requirements**: FR-015; NFR-007, NFR-008; C-007 through C-010.
- **Affected surfaces**: `using-components.md`, optional measured budget update, validation record.
- **Sequencing**: Documentation follows the final public selectors. Full gates follow regeneration
  and final build; acceptance follows independent WP approval.
- **Risk**: A local generator pass followed immediately by `--check` is self-confirming. Commit
  generated files, rerun `--check`, and require `git status --porcelain` empty.

## Gate Enumeration

The single WP must run and record, as applicable:

1. Focused source-contract Playwright tests (red then green).
2. Component browser spec in every configured project; Chromium-specific a11y tree and forced
   colors where engine support is required.
3. `node scripts/build-styles-only-markup.mjs` and `--check`.
4. Styles package build and package export resolution.
5. `npm run quality:all` and targeted stylelint.
6. `npm run test` plus the repository's suite self-test (expected no new behavior mutation arm).
7. Storybook production build and `node scripts/run-axe-storybook.js`.
8. Visual-regression suite with CI-authoritative baselines/diffs.
9. Expected-story ratchet, story load, console-error, `.sk-light`, and token checks.
10. Negative scans for element/manifest/wrapper/behavior/mutation/application/domain additions.
11. Real 200% browser-zoom evidence including document scroll metrics and focused-control bounds.
12. Final regeneration/no-op checks, affected builds, `git diff --check`, and clean tree.

Token catalogue generation/check is a no-op gate unless the token file changes; element CSS,
markup, manifest, wrapper, Vue declaration, and size generators must show no diff. No release or
publication command is run.
